# 再設計・再実装コマンド

一度実装してテストと修正を繰り返した後に、知見をまとめて**ゼロから再設計・再実装**するワークフロー。
実装は**レビューしやすいコミット単位に分割**して段階的に進める。

## 目的

- 試行錯誤で汚れたコードを、得た知見をもとにクリーンに書き直す
- 既存実装を退避して比較・参照可能にする
- 設計ドキュメントを先に作り、実装前にレビューできるようにする
- コミットを論理単位に分けて、レビュアーが差分を追いやすくする

## 変数定義

- `$ARGUMENTS` の先頭トークン: 対象ファイルまたはディレクトリのパス
- `$ARGUMENTS` の残り: 再設計の背景・修正点の概要（任意）

## Step 0: 対象の確認

`$ARGUMENTS` から対象ファイル/ディレクトリと背景を把握する。
指定がない場合は、`git diff HEAD` と `git status` を確認してユーザーに対象を確認する。

## Step 1: 現在の実装を退避する

### 退避先ディレクトリの作成

退避先は `.claude/backups/<YYYYMMDD_HHMMSS>_<対象名>/` とする。

```bash
BACKUP_DIR=".claude/backups/$(date +%Y%m%d_%H%M%S)_backup"
mkdir -p "$BACKUP_DIR"
```

### 実装ファイルを退避

対象ファイルをコピーして退避する。git で追跡されていない生成ファイルも含める。

```bash
# 対象ディレクトリごとコピー
cp -r <対象パス> "$BACKUP_DIR/"

# git diff も退避（パッチとして保存）
git diff HEAD > "$BACKUP_DIR/changes.patch"
```

### 退避完了の確認

退避先に以下を保存したことをユーザーに報告する：
- コピーしたファイル一覧
- `changes.patch`（git diff のパッチ）
- 退避先のパス

## Step 2: 現在の実装の問題点を洗い出す

退避したコードと git diff を読み、以下の観点で問題点を整理する：

### 分析観点

| 観点 | 確認内容 |
|------|---------|
| 設計の歪み | テストで判明した前提の誤り、後付けのパッチ |
| 型・インターフェース | 途中で変わった型定義、不整合な命名 |
| 重複・冗長 | コピペ、使われなくなったコード |
| エラーハンドリング | 後付けで増えた例外処理 |
| テスト容易性 | テストで苦労した箇所（依存が密結合など） |

分析結果を箇条書きで整理し、**ユーザーに確認して合意を得てから次のステップへ進む**。

## Step 3: 再設計ドキュメントを作成する

退避先に `DESIGN.md` として設計書を作成する。

### 設計書の構成

```markdown
# 再設計: <対象名>

## 背景・目的
（前回実装で判明した問題と、今回の再設計の狙い）

## 変更の方針
（前回との差分、廃止する設計、採用する設計）

## インターフェース定義
（型、関数シグネチャ、API）

## 処理フロー
（シーケンス、データフロー）

## コミット計画
（実装をどの単位でコミットに分けるか。Step 4 で使う）

## 実装方針
（ファイル構成、命名規則、注意点）

## 今回やらないこと
（スコープ外の明示）
```

設計書を作成したら、**ユーザーに確認して承認を得てから実装へ進む**。
特に「コミット計画」はユーザーと合意する。

## Step 4: コミット計画を立てる

設計書の「コミット計画」をもとに、実装をコミット単位に分割する。

### コミット分割の原則

**良いコミット単位の基準**：
- レビュアーが「この変更は何をしているか」を一目で把握できる
- 単独でビルドが通る（壊れた状態をコミットしない）
- 1コミット = 1つの論理的な変更（型定義、ロジック、テスト、など）

**典型的な分割パターン**：

```
feat: 型定義・インターフェースを追加
  → 新しい型・enumのみ。ロジックは含まない。

feat: <機能名>のコアロジックを実装
  → ビジネスロジックの本体。型定義を参照。

feat: <機能名>をサービス・コントローラーに組み込む
  → 既存コードへの統合。単体で動作確認可能な単位。

test: <機能名>のユニットテストを追加
  → テストのみ。実装コードは変更しない。

refactor: <旧実装>を削除・整理
  → 不要になった旧コードの削除。動作変更なし。
```

**避けるべきパターン**：
- 型定義・ロジック・テスト・削除を1コミットにまとめる
- "WIP" や "fix" だけのメッセージ
- ビルドが通らない途中状態のコミット

コミット計画を表形式でユーザーに提示し、確認を得てから実装へ進む：

| # | コミットメッセージ（案） | 含まれる変更 | ビルド確認 |
|---|------------------------|------------|----------|
| 1 | feat: ... | ファイルA, B | 必須 |
| 2 | feat: ... | ファイルC | 必須 |

## Step 5: 実装とコミットを交互に進める

コミット計画の順に、**1コミット分実装 → 確認 → コミット** を繰り返す。

### 各コミットの手順

#### 5-1. 実装

そのコミット分のファイルだけを実装する。次のコミット分には手をつけない。

実装の原則：
- 退避したコードをコピペしない（知見だけを活かす）
- 型定義から先に書く
- 各関数・コンポーネントは単一責任を守る
- コメントは「なぜ」だけ書く

#### 5-2. ビルド・Lint・テスト確認

プロジェクトのビルド・Lint・テストコマンドを実行する。コマンドは CLAUDE.md、`package.json` の scripts、`Makefile`、`pyproject.toml` などから確認する。

- 型チェック・ビルド（変更内容に応じて選択）
- Lint（必須）
- テスト（変更内容に応じて選択）

エラーがある場合は修正してから次へ進む。
**ビルドが通らない状態でコミットしない。**

#### 5-3. コミット

`/commit` コマンドを使ってコミットを作成する。

コミットメッセージのフォーマット（Conventional Commits）：
```
<type>: <変更の要約（日本語可）>

（必要があれば補足。なぜこの変更をするか、前回実装との違いなど）
```

- `feat`: 新機能・新しい実装
- `fix`: バグ修正
- `refactor`: 動作を変えないリファクタリング
- `test`: テストの追加・修正
- `chore`: ビルド設定・ツールの変更

コミット後、次のコミット分の実装へ進む。

## Step 6: 全コミット完了後の確認

すべてのコミットが完了したら：

```bash
# コミット一覧を確認
git log --oneline -<コミット数>

# 全体の差分を確認
git diff <ベースブランチ>...HEAD
```

前回実装との比較：
- 退避先の `changes.patch` と現在の `git diff <ベースブランチ>...HEAD` を比較
- 改善された点を列挙

## 完了報告

以下をユーザーに報告する：

1. **退避先パス**: 前の実装の保存場所
2. **コミット一覧**: 作成したコミットと各コミットの概要
3. **改善点**: 前回実装と比べて良くなった点
4. **残課題**: 今回対応しなかった事項

## 注意事項

- **退避は必ず先に行う**: 実装を始める前に退避を完了させる
- **設計・コミット計画承認を得てから実装**: Step 3/4 でユーザーの OK を待つ
- **コミットは計画通りに分ける**: 計画外の変更が出た場合はユーザーに確認
- **退避先は削除しない**: セッション終了まで保持する
- 退避ファイルは `.gitignore` の対象（`.claude/backups/` は git 管理外）
