# コード変更レビューコマンド

## 目的

現在のブランチの変更内容に対してレビューを実施し、指摘一覧を出力します。修正は行いません。

## 変数定義

- base-branch: $1 のこと。比較対象のベースブランチ。省略時はリポジトリのデフォルトブランチ（`git symbolic-ref --short refs/remotes/origin/HEAD` で確認）。判断できない場合はユーザーに確認する

## 処理フロー

### 1. 変更内容の把握

```bash
# 現在のブランチを確認
git branch --show-current

# ベースブランチとの差分を取得
git diff {base-branch}...HEAD

# 変更ファイル一覧
git diff --name-only {base-branch}...HEAD

# ステージされていない変更も確認
git status
git diff
```

### 2. レビュー

差分のあるファイルを全て読み込み、以下の観点と具体的なチェック項目に基づいてレビューしてください。

#### レビュー観点と具体的チェック項目

| 観点                     | 具体的なチェック項目                                                                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --- | ------------------------------------------------------------------------------------ |
| **バグ・ロジックエラー** | 条件分岐の漏れ、off-by-one、null/undefinedの未考慮、境界値チェックの欠如、nullish coalescing (`??`) と or (`                                                                         |     | `) の誤用、配列の空チェック漏れ、非同期処理の `await` 漏れ、Promise の未ハンドリング |
| **型安全性**             | `any` 型の使用、`@ts-ignore` / `@ts-expect-error` の使用、不適切な型アサーション (`as`)、Optional Chaining (`?.`) の過剰使用、型ガードの不足、ジェネリクスの型パラメータ欠如         |
| **セキュリティ**         | SQLインジェクション、XSS、コマンドインジェクション、機密情報（API キー、パスワード等）のハードコード、環境変数の直接埋め込み、ユーザー入力の未サニタイズ、シェルコマンドの文字列構築 |
| **エラーハンドリング**   | catch 節の空実装、エラー情報の握りつぶし（`catch (e) {}`）、不適切なエラーメッセージ、リトライロジックの欠如（外部 API 呼び出し）、エラーログの不足                                  |
| **パフォーマンス**       | N+1 クエリ、ループ内の `await`（並列化可能な場合）、不要な再レンダリング（React）、重複 API 呼び出し、大量データのメモリ保持                                                         |
| **命名・可読性**         | 変数・関数名の不明瞭さ、マジックナンバー、過度に長い関数（50行超）、ネストが深い条件分岐（3階層超）、過度に複雑なロジック                                                            |
| **既存コードとの一貫性** | 命名規則（camelCase/snake_case/PascalCase）の混在、インポート順序の不統一、ログ出力形式の不統一、エラーハンドリングパターンの不統一                                                  |

#### 指摘の出力形式

**重要**: 各指摘は以下の統一形式で記載してください。

````markdown
#### 指摘 {番号}: [{観点}] {概要}

**対象ファイル**: `{ファイルパス}:{行番号}`

**問題点**: {具体的な問題の説明}

**修正前**:

```{言語}
{現在のコード}
```

**修正案**:

```{言語}
{修正後のコード}
```

**修正理由**: {なぜこの修正が必要か}
````

### 3. レビュー結果の出力

レビュー結果は以下の構造で出力してください：

```markdown
## 📋 レビュー結果

### 🔍 検出した指摘

#### 指摘 1: [{観点}] {概要}

**対象ファイル**: `{ファイルパス}:{行番号}`

**問題点**: {説明}

**修正前**:
...

**修正案**:
...

**修正理由**: {説明}

---

### 📊 指摘サマリ

| 観点                 | 件数      |
| -------------------- | --------- |
| バグ・ロジックエラー | {N}件     |
| 型安全性             | {N}件     |
| セキュリティ         | {N}件     |
| エラーハンドリング   | {N}件     |
| パフォーマンス       | {N}件     |
| 命名・可読性         | {N}件     |
| 既存コードとの一貫性 | {N}件     |
| **合計**             | **{N}件** |

### 💡 追加の推奨事項（あれば）

- {テストの追加が必要な箇所}
- {リファクタリングを推奨する箇所}
- {ドキュメント更新が必要な箇所}
```

## 注意事項

- レビュー対象は**変更差分のあるファイルのみ**です。変更に関係ないファイルは対象外です
- コーディングスタイルの好みに関する指摘（セミコロンの有無等）は対象外です。linterやformatterの責務はそちらに委ねてください
- テストファイルの追加・修正は推奨事項として報告のみ行います
- **指摘は必ず統一形式で出力し、ファイルパス:行番号、修正前コード、修正案、修正理由を必ず含めてください**
- **このコマンドはファイルの修正を行いません。修正も行いたい場合は `develop:review-and-fix` を使用してください**
